# Docker Compose Deployment Reference

This reference supports the `deploy-docker-compose` skill.

When a current checkout of `thecrowler-deployment-support` is available,
prefer inspecting the live generator and templates because deployment defaults
may change between releases.

## Canonical Repository Files

| Purpose                 | Repository path                             |
| ----------------------- | ------------------------------------------- |
| Compose generator       | `docker-compose/generate-docker-compose.sh` |
| Compose user guide      | `docker-compose/README.md`                  |
| Environment template    | `common/env/env_template`                   |
| Local CROWler config    | `common/config/config.default`              |
| Remote config bootstrap | `common/config/config.default.remote`       |
| Agent-wide rules        | `AGENTS.md`                                 |

## Official CROWler Images

| Component | Image                       | Version variable      |
| --------- | --------------------------- | --------------------- |
| Database  | `zfpsystems/crowler-db`     | `CROWLER_VERSION`     |
| Engine    | `zfpsystems/crowler-engine` | `CROWLER_VERSION`     |
| API       | `zfpsystems/crowler-api`    | `CROWLER_VERSION`     |
| Events    | `zfpsystems/crowler-events` | `CROWLER_VERSION`     |
| VDI       | `zfpsystems/crowler-vdi`    | `CROWLER_VDI_VERSION` |

The VDI image is versioned independently because its release lifecycle also
includes Selenium and browser components.

Do not assume that `CROWLER_VERSION` and `CROWLER_VDI_VERSION` use matching
version strings.

## Core Environment Variables

Important deployment variables include:

```text
CROWLER_VERSION
CROWLER_VDI_VERSION
DOCKER_DB_HOST
DOCKER_POSTGRES_PASSWORD
DOCKER_CROWLER_DB_USER
DOCKER_CROWLER_DB_PASSWORD
```

Additional variables may be required by CROWler features, plugins, rules,
telemetry, proxies, email connectors, or external integrations.

Never invent secret values.

## Generator Inputs

The current generator supports configuration for:

```text
Engine count
VDI count
PostgreSQL inclusion
Prometheus Pushgateway inclusion
API inclusion
Events inclusion
Jaeger inclusion
global CPU limits
Engine CPU limits
VDI CPU limits
management-service CPU limits
Engine memory limits
VDI memory limits
management-service memory limits
telemetry memory limits
Docker Swarm mode
```

Read `generate-docker-compose.sh --help` and the actual argument parser before
relying on a long-form option name.

For automated execution, prefer explicit arguments so the generator does not
wait for interactive input.

## Generated Components

Depending on generator options, a Compose deployment may contain:

```text
crowler-db
crowler-api
crowler-events
crowler-engine-N
crowler-vdi-N
crowler-jaeger
crowler-push-gateway
```

Engine and VDI services are generated as explicitly named services.

Do not assume that generic `docker compose --scale` behavior is equivalent to
the topology produced by the generator.

## Networks

The deployment contains a general CROWler network and may contain one network
for each generated VDI.

Engine-to-VDI network access is part of the generated topology and must be
preserved when modifying scaling behavior.

When Engine and VDI counts are different, inspect the generated mapping and
verify that every Engine references an existing VDI.

## Persistent Volumes

Persistent volumes may include:

```text
db_data
engine_data
api_data
events_data
```

Treat database volumes as persistent user data.

Never delete volumes as part of routine deployment validation or
troubleshooting.

## Common Ports

The first generated VDI normally exposes services for:

| Service                  | Container port |
| ------------------------ | -------------: |
| Selenium                 |         `4444` |
| VDI management           |         `4445` |
| VNC                      |         `5900` |
| noVNC                    |         `7900` |
| Chrome DevTools Protocol |         `9222` |

Additional VDI instances use unique host-side port assignments generated by
the script.

Other commonly exposed services include:

| Service                |    Port |
| ---------------------- | ------: |
| CROWler API            |  `8080` |
| CROWler Events         |  `8082` |
| PostgreSQL             |  `5432` |
| Jaeger UI              | `16686` |
| OpenTelemetry gRPC     |  `4317` |
| Prometheus Pushgateway |  `9091` |

Always inspect the generated Compose file for the actual host-side mapping.

## Local and Remote CROWler Configuration

Local configuration template:

```text
common/config/config.default
```

Remote bootstrap template:

```text
common/config/config.default.remote
```

Do not assume that the presence of these templates means a generated
deployment is automatically mounting or distributing them.

Inspect the current Compose generator before claiming that a configuration
file is wired into a container.

## Environment File Semantics

Docker Compose has two related but distinct environment mechanisms:

```text
docker compose --env-file FILE
```

controls Compose variable interpolation.

A service declaration such as:

```yaml
env_file:
  - .env
```

injects variables into that container.

When both mechanisms are used, verify that their paths resolve to the intended
file.

Do not assume that passing `--env-file` changes the path referenced by a
service-level `env_file:` declaration.

## Validation

A generated deployment should pass:

```bash
docker compose config
```

The validation context must use the same environment settings intended for the
real deployment.

After rendering, also verify:

```text
no CROWler build: directives
expected zfpsystems images
expected image tags
requested Engine count
requested VDI count
valid Engine-to-VDI references
valid networks
valid volumes
no unexpected port collisions
requested optional services
```

## Safety

Do not:

```text
delete persistent volumes
erase database data
overwrite user credentials
commit .env secrets
replace official images with source builds
force amd64 without an explicit requirement
invent image tags
silently resolve conflicting repository defaults
```

When repository documentation, templates, and generator behavior disagree,
surface the discrepancy and prefer observed generator behavior when explaining
what the current deployment will actually produce.
